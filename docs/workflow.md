## A. 데이터를 저장하는 기능을 만들 때

`applications`(신청 페이지)를 만들 때 쓴 순서입니다. **가장 자주 쓰게 될 순서입니다.**

| # | 단계 | 왜 이 순서인가 |
|---|---|---|
| 1 | **무엇을 저장할지 정한다** | 컬럼을 나중에 바꾸는 건 비싸다 |
| 2 | **누가 무엇을 할 수 있는지 표로 그린다** | 코드를 쓰기 전에 권한을 정한다 |
| 3 | `create table` + `alter table ... enable row level security` | **테이블을 만들면 RLS를 즉시 켠다** |
| 4 | `grant` — 테이블 단위 권한 | SQL로 만든 테이블은 **자동으로 안 붙는다** |
| 5 | `create policy` — 행 단위 권한 | GRANT와 **같은 방향**이어야 통과 |
| 6 | `check` 제약 — 값의 형식 | 진짜 방어는 여기뿐 |
| 7 | **💥 curl 로 공격해본다** | 브라우저를 빼고 직접 두드린다 |
| 8 | 화면(HTML/JS)을 붙인다 | 방어가 끝난 뒤에 화면 |
| 9 | **브라우저에서 동작 확인** | |
| 10 | `db/0NN_이름.sql` 로 기록 | 웹에서 실행한 SQL은 **아무 데도 안 남는다** |
| 11 | 커밋 · push (= 배포) | |

### 2단계 — 권한 표 그리는 법

표를 먼저 그리면 빠뜨리지 않습니다. `applications` 의 경우:

| 명령 | 누가 | GRANT(문 앞) | RLS(방 안) |
|---|---|---|---|
| INSERT | 누구나 | `anon, authenticated` | `with check (true)` |
| SELECT | 관리자만 | `authenticated` | `exists (admins ... auth.uid())` |
| UPDATE | 아무도 | **안 줌** | **안 만듦** |
| DELETE | 아무도 | **안 줌** | **안 만듦** |

> **안 주는 칸을 비워두는 게 설계입니다.** 나중에 필요해지면 그때 추가합니다.
> RLS는 정책이 없으면 자동 차단이므로, **안 만드는 것 = 막는 것**입니다.

### 7단계 — 공격 방법

> 📁 **리눅스 프롬프트** — 브라우저의 검증을 전부 건너뛰고 API를 직접 두드립니다.
> JS 필터도 HTML `pattern` 도 여기서는 존재하지 않습니다.

```bash
# 읽기가 막히는지
curl "$URL/rest/v1/applications?select=*" -H "apikey: $KEY"

# 잘못된 값이 막히는지
curl -X POST "$URL/rest/v1/applications" -H "apikey: $KEY" \
  -H "Content-Type: application/json" \
  -d '{"name":"공격","phone":"abc"}'
```

**결과 읽는 법** — 어디서 막혔는지가 코드에 드러납니다.

| 응답 | 의미 |
|---|---|
| `401 permission denied` | **GRANT** 에서 막힘 (문 앞) |
| `200 []` (빈 목록) | **RLS** 에서 막힘 (방 안) — 정보를 덜 흘림 |
| `400 violates check constraint` | **CHECK** 에서 막힘 (값 형식) |
| `201 Created` | 통과 — 의도한 것인지 확인 |

## B. 화면(페이지)을 만들 때

| # | 단계 | 주의 |
|---|---|---|
| 1 | `*.html` — 구조만 | `onclick=` · `style=` **인라인 금지** |
| 2 | `style.css` — 모양 | |
| 3 | `*.js` — 동작 | `addEventListener` 로 연결 |
| 4 | 그 페이지에 **필요한 권한만** 쓴다 | 신청 페이지는 `.select()` 를 붙이지 않음 |
| 5 | 오류를 화면에 그대로 띄운다 | 학습 단계에서는 감추지 않는다 |
| 6 | 브라우저 확인 → push | push = 자동 배포 |

> ⚠️ **화면을 감추는 건 보안이 아닙니다.**
> 개발자도구로 `hidden` 을 지우면 영역은 드러납니다. 내용이 비어 있는 이유는 RLS 때문입니다.
> **화면은 편의, 방어는 DB.**

## C. 오류 · 장애가 났을 때

어떤 장애든 순서는 같습니다. **이 순서를 벗어나면 헤맵니다.**

```
① 증상 확인      무엇이 안 되는가 (추측 말고 현상)
② 메시지 해석    영어 원문을 우리말로 옮긴다
③ 상태 조회      지금 실제로 어떤 상태인가
④ 원인 추정      ②③ 을 근거로. 여러 개면 확인이 쉬운 것부터
⑤ 조치          한 번에 하나씩 (여러 개 바꾸면 뭐가 들었는지 모름)
⑥ 💥 검증        "고쳤다" 와 "고쳐진 걸 확인했다" 는 다르다
⑦ 기록          runbook/ 에 남긴다
```

### ② 에 쓰는 메시지 구분

| 메시지 | 어디서 막혔나 |
|---|---|
| `No such file or directory` | 경로가 틀림 — **파일이 없음** |
| `Permission denied` | 경로는 맞음 — **권한이 없음** |
| `Connection refused` | **닿지도 못함** — 포트가 닫힘 |
| `password authentication failed` | **닿았음** — 주소·포트는 맞고 인증만 실패 |

> 뒤의 두 개를 구분하면 **찾을 범위가 절반으로 줄어듭니다.**

### ③ 에 쓰는 조회 명령

> 📁 **리눅스 프롬프트** — 무엇이 돌고 있고 어떤 포트를 쓰는지 봅니다. (조회만, 무해)

```bash
systemctl status nginx     # 이 서비스가 살아 있나
ss -tln                    # 어떤 포트가 열려 있나
tail -50 /var/log/nginx/error.log   # 최근 무슨 일이 있었나
ls -l 경로                  # 소유자와 권한
```

### ⑦ 기록은 언제 남기나

**30분 이상 막혔던 것**은 남깁니다. 며칠 뒤면 잊고, 같은 곳에서 또 막힙니다.
형식은 [`runbook/README.md`](runbook/README.md) 의 템플릿.

## D. 서버 설정 파일을 고칠 때

> ⚠️ **설정 하나 잘못 고치면 서비스가 안 뜹니다.** 순서를 지키면 되돌릴 수 있습니다.

```
① 백업     cp 파일 파일.bak.날짜      ← 되돌릴 수단을 먼저 만든다
② 수정     sudo nano 파일
③ 검사     nginx -t                  ← 재시작 전에 문법 검사
④ 재시작   sudo systemctl reload nginx
⑤ 검증     실제로 접속해본다
```

**③ 을 건너뛰지 마세요.** 문법이 틀린 채 재시작하면 nginx가 아예 안 뜹니다.
검사에서 걸리면 **아직 예전 설정으로 돌고 있으므로 서비스는 살아 있습니다.**

되돌리기:

```bash
sudo cp 파일.bak.날짜 파일 && nginx -t && sudo systemctl reload nginx
```

## E. 커밋하기 전 점검

> 📁 **Git Bash / 리눅스 프롬프트** — 올리면 안 되는 게 섞였는지 봅니다.

```bash
git status                              # 무엇이 올라가는지
git ls-files | grep -E "\.(gz|csv|dump)$"   # 백업 파일이 잡히나 (아무것도 안 나와야 정상)
git diff                                # 내용 확인
```

| 확인 | 왜 |
|---|---|
| `.env` 가 안 잡히나 | 비밀번호 유출 |
| `*.sql.gz` · `*.csv` 가 안 잡히나 | **개인정보 유출** |
| 키가 코드에 박혀 있나 | Publishable 은 무방, **Secret 은 금지** |

> 💥 **Git 은 지워도 과거 커밋에 남습니다.**
> 한 번 올라간 개인정보는 `git rm` 으로 지워도 이력에 그대로 있고,
> 누가 복제(clone)해 갔다면 **회수할 수 없습니다.** 들어가지 않게 막는 것이 유일한 방법입니다.

**설계도는 공개, 데이터는 비공개** — `db/*.sql`(구조)는 올리고, `*.sql.gz`(내용)는 안 올립니다.

## G. 💥 복구 테스트 (아직 안 해봄)

> **해본 적 없는 백업은 백업이 아닙니다.**
> 파일이 생기는 것과 그 파일로 되살릴 수 있는 것은 **다른 이야기**입니다.

⚠️ **반드시 빈 DB에 복구합니다.** 실제 DB에 하면 기존 데이터를 덮어씁니다.

```
① 압축 검사      gzip -t 백업파일
② 연습용 DB 생성  createdb restore_test
③ 복구           gunzip -c 백업파일 | psql -d restore_test
④ 확인           건수·내용이 맞는가
⑤ 정리           dropdb restore_test
```

⑤ 까지 마쳐야 "백업이 있다"고 말할 수 있습니다.

## H. 앞으로의 순서 (큰 그림)

작은 것부터 올라갑니다. **각 단계는 앞 단계가 손에 붙은 뒤에** 갑니다.

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | Supabase 로 **기능**을 만들어본다 (RLS·Auth·Storage) | ✅ |
| 2 | WSL2 로 **서버**를 만져본다 (nginx·PostgreSQL·권한) | ✅ |
| 3 | **백업과 복구**를 갖춘다 | 🔶 백업만 됨 |
| 4 | 내부용 작은 도구를 실제로 운영 (runbook 사이트) | ⬜ |
| 5 | VPS 를 사서 **혼자 세팅** (SSH·방화벽·SSL·자동 업데이트) | ⬜ |
| 6 | 홈페이지 이전 | ⬜ |
| 7 | CRM 자체 구축 | ⬜ |

> 쇼핑몰은 **카페24 유지**입니다. 결제·전자상거래법·정산 책임까지 떠안게 됩니다.
> 자세한 판단 근거는 [`feature-map.md`](feature-map.md) 의 C·H 장.

### 각 단계에서 "됐다"고 볼 기준

| 단계 | 통과 기준 |
|---|---|
| 3 | **복구 테스트를 해봤다.** 백업이 다른 장소에도 있다 |
| 4 | 나 말고 **다른 사람이 쓰고 있다** |
| 5 | 설정을 잘못해서 **접속이 막혀봤고, 혼자 풀었다** |
| 6 | 장애가 나도 **runbook 보고 혼자 복구**된다 |
