# 실서비스 기능 지도

실제 라이브 서비스에 필요해질 기능을 **"Supabase로 되는가 / 별도 비용인가 / 직접 만들어야 하는가"** 로 정리했습니다.
설계 단계에서 미리 확인해두면 나중에 구조를 갈아엎지 않습니다.

> ⚠️ **요금·지원 범위는 자주 바뀝니다.** 실제 도입 시 공식 문서로 재확인하세요.
> 이 문서는 2026-09 기준으로 확인한 내용입니다.

## 표기

| 표시 | 뜻 |
|---|---|
| ✅ | Supabase 기본 제공. 추가 계약 불필요 |
| 💰 | 기능은 제공하나 **외부 업체 계약·건당 비용** 발생 |
| 🔧 | **직접 구현** 필요 (서버 코드) |
| 🇰🇷 | **국내 특수** — 해외 서비스로 해결 안 됨 |

## A. 회원 / 인증

| 기능 | 상태 | 비고 |
|---|---|---|
| 이메일 + 비밀번호 로그인 | ✅ | 현재 관리자 로그인이 이 방식 |
| 비밀번호 재설정 | ✅ | 이메일 발송 필요 (B 참조) |
| 이메일 인증 | ✅ | 발송 한도 주의 |
| **카카오 로그인** | ✅ | 기본 지원 목록에 있음 |
| 구글 · 애플 · 페이스북 로그인 | ✅ | 기본 지원 |
| **네이버 로그인** | 🔧 | 기본 목록에 **없음**. OAuth2 호환이라 직접 등록은 가능 |
| **전화(SMS) 인증** | 💰 | Supabase는 **문자를 보내지 않음.** Twilio 등 별도 계약 + 건당 비용 |
| **본인확인 (실명·성인인증)** | 🇰🇷🔧 | NICE·KCB 등 **국내 본인확인기관과 별도 계약.** 해외 서비스로 대체 불가 |
| 다중 인증(MFA) | ✅ | 플랜 확인 필요 |
| 권한 분리 (관리자/일반) | ✅ | RLS + `admins` 명단 방식 (현재 구현됨) |

### ⚠️ 전화 인증의 함정

공식 문서 경고:
> "To keep SMS sending costs under control, make sure you adjust your project's rate limits and configure CAPTCHA."
> → 문자 발송 비용을 통제하려면 요청 제한과 CAPTCHA를 설정하세요.

**누가 인증번호 요청을 반복하면 그만큼 요금이 나갑니다.** 자동화 공격 시 요금 폭탄.
기본 방어: 60초에 1회 제한, 1시간 후 만료.

## B. 알림 / 발송

| 기능 | 상태 | 비고 |
|---|---|---|
| 회원가입·비밀번호 재설정 메일 | ✅ | **단, 기본 발송 한도가 낮음** |
| 대량 이메일 (공지·마케팅) | 💰 | SendGrid·Resend·Mailgun 등 연결 |
| **SMS 발송** | 💰🇰🇷 | 국내는 알리고·솔라피·NCP SENS 등. Supabase 지원 목록은 전부 해외 업체 |
| **카카오 알림톡** | 🇰🇷💰 | 국내 전용. 발송 대행사 계약 필요 |
| 푸시 알림 (앱) | 🔧 | 별도 구현 |

> **이메일 발송 한도를 반드시 확인하세요.** Supabase 기본 발송은 개발·테스트용 수준입니다.
> 실서비스에서 회원가입 메일이 안 가면 가입 자체가 막힙니다.

## C. 결제 — 전부 별도

| 기능 | 상태 | 비고 |
|---|---|---|
| 카드 결제 | 🇰🇷💰🔧 | PG사 계약 (토스페이먼츠·KG이니시스·나이스페이 등) |
| 간편결제 (카카오·네이버페이) | 🇰🇷💰🔧 | 각각 별도 계약 |
| 정기결제 | 🇰🇷💰🔧 | |
| **결제 검증** | 🔧 | **반드시 서버에서.** Secret key가 필요해 브라우저 불가 |
| 현금영수증·세금계산서 | 🇰🇷💰 | |
| 에스크로 | 🇰🇷 | 전자상거래법 요건 |

> **결제가 붙는 순간 서버가 필요합니다.** Supabase Edge Functions 로 대체 가능하지만,
> "브라우저만으로 끝나는 구조"는 여기서 끝납니다.
>
> 그리고 **쇼핑몰 전체를 직접 만드는 건 여전히 권하지 않습니다** — 카페24가 대신 지고 있는
> 법적 책임(청약철회·표시광고·정산)까지 떠안게 됩니다.

## F. 서버가 필요해지는 지점

브라우저만으로 안 되는 것들입니다. **비밀 키를 써야 하는 작업**이 전부 여기 해당합니다.

| 작업 | 왜 서버가 필요한가 |
|---|---|
| 결제 검증 | PG사 Secret key |
| SMS·알림톡 발송 | 발송 업체 키 |
| 카페24 API 연동 | API 키 |
| 본인확인 | 기관 인증 키 |
| 정기 배치 (집계·정리) | 브라우저는 꺼져 있음 |

**해결책:** Supabase **Edge Functions** — 서버를 만들지 않고 서버 코드만 올리는 방식.
비밀 키를 거기 두고, 브라우저는 그 함수를 부릅니다.

## H. 법규 — 기술로 해결되지 않는 것 🇰🇷

**여기가 가장 자주 빠뜨리는 영역입니다.**

| 항목 | 필요 시점 |
|---|---|
| **개인정보 처리방침** 게시 | 개인정보를 받는 순간 |
| **수집·이용 동의** 절차 | 〃 |
| 제3자 제공 동의 | 외부에 넘길 때 |
| **국외 이전 고지·동의** | 해외 서비스 이용 시 — **검토 필요** |
| 민감정보 별도 동의 | **임산부·육아 = 건강 관련 정보일 수 있음** |
| 이용약관 | 회원 서비스 시작 시 |
| 전자상거래법 표기 | 판매가 있을 때 |
| 개인정보 보호책임자 지정 | 일정 요건 시 |

> ⚠️ **이건 코드로 해결되지 않습니다.** 법무 검토 영역이고,
> 위반 시 과징금이 기술 사고보다 클 수 있습니다.
>
> 특히 **민감정보** 항목 — 출산예정일·임신주차·아이 생년월일이 건강 관련 정보로
> 해석될 여지가 있습니다. 실서비스 전 반드시 확인하세요.

## 요약 — 어디까지 Supabase로 가능한가

```
회원 · 데이터 · 파일 · 권한        →  ✅ 대부분 가능
이메일 · SMS 대량 발송             →  💰 외부 업체 연결
결제 · 본인확인 · 알림톡           →  🇰🇷 국내 업체와 별도 계약 + 서버 필요
법규 대응                          →  기술 아님. 법무 영역
```

**"Supabase로 안 되는 것"의 대부분은 국내 특수 영역**입니다.
네이버클라우드로 옮긴다고 해결되지 않습니다 — **어차피 PG사·본인확인기관·발송대행사와 각각 계약**해야 합니다.

즉 **인프라를 어디에 두느냐와 이 항목들은 별개 문제**입니다.

## 설계 시 판단 순서

```
1. 이 기능이 정말 필요한가          →  대부분 "아직 아님"
2. 비밀 키를 써야 하는가            →  그렇다면 서버(Edge Functions) 필요
3. 국내 업체 계약이 필요한가        →  🇰🇷 표시 항목
4. 법적 요건이 따라붙는가           →  H 항목
5. 그다음에 구현 방법을 정한다
```

**1번에서 걸러지는 게 대부분입니다.** 미리 만들어둔 기능은 대개 안 쓰이고, 관리 부담만 남습니다.
