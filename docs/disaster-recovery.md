# 재해 복구 (Disaster Recovery)

> **"전부 날아가면 어떻게 되살리는가"**
>
> 백업 **파일을 만드는 법**은 [`../scripts/README.md`](../scripts/README.md).
> 이 문서는 **그 파일로 실제로 되살리는 순서**입니다.

⚠️ **사고가 난 뒤에 이 문서를 처음 읽으면 늦습니다.** 평소에 한 번 훑어두세요.

# 1. 자산 지도 — 무엇이 어디에 있나

되살리려면 **무엇이 어디에 있는지**부터 알아야 합니다.

| 자산 | 어디에 | 사본 | 잃으면 |
|---|---|---|---|
| **화면 코드** (HTML/CSS/JS) | GitHub + 내 PC + Vercel | 3곳 | 🟢 거의 안전 |
| **DB 구조** (테이블·정책·권한) | `db/*.sql` → GitHub | 2곳 | 🟢 순서대로 실행하면 재현 |
| **DB 데이터** (신청 내역) | Supabase + `~/site-backup/output/` | 2곳 | 🟡 **둘 다 같은 날 잃을 수 있음** |
| **첨부 이미지** | Supabase Storage **뿐** | **1곳** | 🔴 **사본 없음** |
| **계정·비밀번호** | 사람 | ? | 🔴 [`secrets-inventory.md`](secrets-inventory.md) 참조 |
| **작업 순서·기록** | `docs/` → GitHub | 2곳 | 🟢 |

> 🔴 **현재 가장 큰 구멍은 첨부 이미지입니다.** DB만 백업하고 있어서,
> 복구해도 *"사진 있음"이라고 기록된 신청서에 사진이 없는* 상태가 됩니다.

# 2. 얼마나 잃고, 얼마나 걸리나

복구를 이야기할 때 쓰는 두 숫자입니다.

| 용어 | 뜻 | 현재 |
|---|---|---|
| **RPO** (Recovery Point Objective) | **얼마나 잃는가** — 마지막 백업 이후의 데이터 | 최대 **1일** (백업이 하루 1회일 때) |
| **RTO** (Recovery Time Objective) | **얼마나 걸리는가** — 복구 완료까지 | **모름** — 해본 적이 없어서 |

> **RTO를 모른다는 건 "복구 계획이 없다"는 뜻입니다.**
> 한 번 해보면 숫자가 나옵니다. → 6장

# 3. 시나리오별 대응

## A. 실수로 데이터를 지웠다 (가장 흔함) 🟡

> ⚠️ **가장 먼저 할 일: 아무것도 더 하지 마세요.**
> 당황해서 이것저것 실행하면 상황이 나빠집니다. **현재 상태를 먼저 백업**합니다.

```
① 지금 상태를 먼저 백업     ← 복구가 실패해도 되돌아올 지점
② 언제 지워졌는지 확인
③ 그 시점 이전의 백업 파일 찾기
④ 💥 연습용 DB에 먼저 복구  ← 실제 DB에 바로 하지 않는다
⑤ 데이터가 맞는지 확인
⑥ 필요한 행만 옮긴다
```

**⑥ 이 핵심입니다.** 보통은 전체를 덮어쓸 게 아니라 **지워진 몇 줄만** 필요합니다.
전체 복구는 그 이후에 들어온 신청까지 날립니다.

## B. Supabase 프로젝트가 정지됐다 🟢

무료 플랜은 **1주일 미사용 시 자동 정지**됩니다. 데이터는 그대로 있습니다.

→ 대시보드에서 `Restore` 클릭. 몇 분 걸립니다.
→ 기록: [`runbook/supabase-free-tier-paused.md`](runbook/supabase-free-tier-paused.md)

> 🟡 **예방:** 주 1회 열어보기. 실서비스는 유료 플랜으로 (정지 없음).

## C. Supabase 프로젝트가 삭제됐다 / 계정을 잃었다 🔴

**전체 재구축**입니다. → 4장

## D. PC가 고장났다 🔴

| | |
|---|---|
| 코드 | 🟢 GitHub에 있음 |
| DB 데이터 | 🟡 Supabase에 원본이 있음 |
| **로컬 백업** | 🔴 **같이 사라짐** |
| WSL 환경 | 🔴 다시 설치 (설정은 `linux-cheatsheet.md` 참조) |

> **원본(Supabase)과 백업(내 PC)이 둘 다 살아 있어야 안전합니다.**
> 지금은 PC 고장 = 백업 전멸입니다. **외부 보관 1곳이 필요한 이유**입니다.

## E. 개인정보가 유출된 것 같다 🔴 — 복구가 아니라 대응

> **이건 기술 문제가 아니라 법적 의무가 따르는 사안입니다.**

```
① 막기        키 교체·정책 차단. 유출 경로를 먼저 끊는다
② 보존        로그를 지우지 않는다 (원인 파악과 증빙에 필요)
③ 범위 확인   무엇이 / 몇 건 / 언제부터
④ 통지        개인정보보호법상 의무 — 지체 없이
⑤ 신고        일정 요건에서 신고 의무
```

⚠️ ④⑤ 는 **기한과 요건이 법으로 정해져 있습니다.** 정확한 기준은 반드시 확인하세요 —
제 설명에 의존하지 마시고, 실서비스 전에 **법무 검토**를 받으시는 게 맞습니다.

# 4. 전체 재구축 순서

Supabase 프로젝트를 통째로 다시 만들어야 할 때입니다.

| # | 단계 | 출처 | 예상 |
|---|---|---|---|
| 1 | 새 프로젝트 생성 (**리전 Seoul**) | [`setup-guide.md`](setup-guide.md) 1단계 | 5분 |
| 2 | `db/*.sql` **번호순으로 실행** | `db/` | 10분 |
| 3 | GRANT·정책 확인 | `queries/check-policies.sql` | 5분 |
| 4 | 관리자 계정 생성 → `admins` 등록 | `queries/manage-admins.sql` | 5분 |
| 5 | Storage 버킷 + 정책 재생성 | `db/006_*.sql` | 10분 |
| 6 | **DB 데이터 복구** | `~/site-backup/output/` | ? |
| 7 | **첨부 파일 복구** | 🔴 **사본 없음** | — |
| 8 | 새 키를 코드에 반영 → push | `app.js` 등 | 5분 |
| 9 | 💥 검증 — 신청·로그인·조회·첨부 | `workflow.md` A-⑦ | 10분 |

> **2단계가 가능한 이유가 `db/` 입니다.**
> Supabase 웹에서 실행한 SQL은 아무 데도 안 남습니다. 그 파일들이 **유일한 설계도**입니다.
> → 그래서 "SQL을 실행했으면 `db/` 에 남긴다"가 규칙입니다.

## 6단계 — 데이터 복구 명령

> 📁 **리눅스 프롬프트**
> ⚠️ **반드시 비어 있는 DB에.** 데이터가 있는 DB에 하면 섞이거나 덮어씁니다.

```bash
gzip -t 백업파일.sql.gz                          # ① 파일이 멀쩡한가
gunzip -c 백업파일.sql.gz | psql "$접속문자열"    # ② 복구
```

`gzip -t` 는 **압축이 깨지지 않았는지** 검사합니다. 아무 메시지도 안 나오면 정상입니다.

# 5. 지금 있는 구멍 (솔직하게)

| 구멍 | 위험 | 해결 |
|---|---|---|
| 🔴 **첨부 이미지 백업 없음** | 복구해도 사진이 없음 | `rclone` + S3 프로토콜 |
| 🔴 **복구 테스트 안 해봄** | 백업이 쓸모없을 수 있음 | 6장 — 30분 |
| 🔴 **백업이 같은 PC에만** | PC 고장 = 전멸 | 암호화 후 외부 1곳 |
| 🟡 **자동 실행 안 됨** (cron 미등록) | 사람이 잊으면 끊김 | `scripts/README.md` |
| 🟡 **계정 정보 미정리** | 복구 중 막힘 | [`secrets-inventory.md`](secrets-inventory.md) |

**우선순위는 위에서부터**입니다.
다만 실질적으로는 **복구 테스트가 먼저**입니다 — 백업이 되는지 모르는 상태에서 다른 걸 늘려봐야 의미가 없습니다.

# 6. 💥 복구 테스트 (아직 안 함)

> **해본 적 없는 백업은 백업이 아닙니다.**
> 파일이 생기는 것과 그 파일로 되살릴 수 있는 것은 **다른 이야기**입니다.

⚠️ **연습용 DB에만** 합니다. 실제 DB에 하면 덮어씁니다.

> 📁 **리눅스 프롬프트**

```bash
# ① 압축이 멀쩡한가 (아무 말 없으면 정상)
gzip -t ~/site-backup/output/db_최신.sql.gz

# ② 연습용 빈 DB 만들기
sudo -u postgres createdb restore_test

# ③ 복구
gunzip -c ~/site-backup/output/db_최신.sql.gz | sudo -u postgres psql -d restore_test

# ④ 확인 — 건수가 맞나
sudo -u postgres psql -d restore_test -c "select count(*) from applications;"

# ⑤ 정리 (⚠️ 연습용 DB만 지웁니다. 이름을 두 번 확인하세요)
sudo -u postgres dropdb restore_test
```

## 기록할 것

테스트하면서 **이 표를 채우면** 복구 계획이 완성됩니다.

| 항목 | 결과 |
|---|---|
| 압축 검사 | ⬜ |
| 복구 중 오류 | ⬜ |
| 건수 일치 | ⬜ |
| 한글이 안 깨지나 | ⬜ |
| **걸린 시간 (= RTO)** | ⬜ |

> **오류가 나는 게 정상입니다.** 그걸 지금 발견하는 게 이 테스트의 목적입니다.
> 진짜 사고가 났을 때 처음 발견하면 손쓸 수 없습니다.
