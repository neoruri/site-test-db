## 증상

사이트는 정상적으로 뜨는데 글 목록 조회가 실패.
화면에 나온 오류:

```
TypeError: Failed to fetch
→ 타입오류: 가져오기 실패
```

`fetch`(브라우저가 서버에 데이터를 요청하는 기능)가 **서버에 닿지도 못한** 상태.
서버가 오류를 돌려준 게 아니라 연결 자체가 안 됨.

## 원인

**Supabase 무료 플랜은 7일간 활동이 적으면 프로젝트를 일시정지할 수 있다.**

공식 문서 원문:
> "We may pause applications on the Free Plan that exhibit **low activity** in a 7-day period
> to save on server resources."
> → 무료 플랜에서 **7일 동안 활동이 적은** 애플리케이션은 자원 절약을 위해 정지될 수 있습니다.

⚠️ **주의해서 읽을 것**
- `no activity`(활동 없음)가 아니라 **`low activity`(활동이 적음)** — 요청이 조금 있어도 정지될 여지가 있다
- `may pause`(정지될 수 **있다**) — 보장이 아니라 **재량**이다
- **무엇이 활동으로 집계되는지 문서에 정의돼 있지 않다.**
  API 요청도 포함될 가능성이 높지만 확인된 바는 없다.

정지되면 프로젝트 도메인(`<프로젝트ID>.supabase.co`)이 DNS에서 사라진다.
그래서 브라우저가 **어디로 연결할지조차 모르는** 상태가 된다.

이번 경우: 마지막 사용 2026-08-19 → 발생 2026-09-07 (약 2주 반 경과).

> 데이터는 삭제되지 않는다. "잠자기"이지 삭제가 아니다.

## 확인 방법

**내 PC 문제인지 상대 서버 문제인지 나누는 게 핵심.**

```powershell
# 기준: 일반 도메인은 되는가
Resolve-DnsName google.com
Resolve-DnsName supabase.com

# 내 프로젝트 도메인
Resolve-DnsName elcgktqkecweekkupjqn.supabase.co

# 공개 DNS로 재확인 (내 PC의 DNS 설정 문제를 배제)
Resolve-DnsName elcgktqkecweekkupjqn.supabase.co -Server 8.8.8.8
```

| 결과 | 판정 |
|---|---|
| 일반 도메인 O, 내 프로젝트만 X | **상대 서버 문제** — 내 코드는 건드릴 필요 없음 |
| 전부 X | 내 PC의 네트워크·DNS 문제 |

리눅스에서는 `nslookup 도메인` 또는 `dig 도메인`.

## 조치

1. https://supabase.com/dashboard 접속
2. 해당 프로젝트 선택
3. `Paused` / `Inactive` 표시 확인
4. **`Restore project`** 또는 **`Resume`** 클릭

⏱️ 복구에 몇 분 걸린다. 완료되면 도메인이 다시 살아난다.

## 재발 방지

**학습 단계:** 주 1회 정도 배포된 사이트를 열어준다.
https://site-test-db.vercel.app — 열기만 해도 글 목록 조회 요청이 발생한다.
대시보드에 들어갈 필요는 없다.

**실서비스 단계: 무료 플랜을 쓰지 않는다.** 정지 정책만의 문제가 아니다.

| 항목 | 무료 플랜의 한계 |
|---|---|
| 자동 정지 | 새벽에 멈춰도 알 방법이 없음 |
| 백업 보관 기간 | 짧음 — 사고 시 복구 범위가 제한됨 |
| 기술 지원 | 없음 |
| 용량·요청 한도 | 제한적 |

회원 데이터(특히 민감정보)를 다루는 서비스라면 감당할 수 없는 위험이다.
실제 운영 시에는 매일 접속이 있으므로 정지 자체는 문제되지 않는다 —
**이 이슈는 사실상 학습 단계에서만 겪는 일이다.**

## 배운 것

**1. `Failed to fetch` 는 "서버가 거절했다"가 아니라 "닿지도 못했다"**

서버가 응답했다면 상태 코드(401, 403, 500 등)가 나온다.
`Failed to fetch` 는 그 이전 단계 — 연결 실패다. 그래서 원인을 **네트워크 쪽**에서 찾아야 한다.

**2. 진단은 "내 쪽"과 "상대 쪽"을 나누는 것부터**

```
연결 실패
 → 다른 도메인은 되나?     된다 → 내 네트워크는 정상
 → 공개 DNS에서도 없나?    없다 → 상대 도메인이 실제로 사라진 것
 → 결론: 내 코드 문제 아님
```

이걸 안 나눴으면 `app.js` 를 뜯어보며 시간을 버렸을 것이다.
**nginx 포트 충돌 때와 같은 흐름** — 문제 범위를 절반씩 잘라 들어간다.

**3. 무료 서비스의 제약은 미리 알아둬야 한다**

기술 문제가 아니라 **요금제 정책** 때문에 멈춘 것이다.
외부 서비스를 쓸 때는 그 서비스의 제한(정지 조건, 요청 한도, 용량)을 먼저 확인해둔다.
