## 왜 확인하는가

**DB를 인터넷에 노출시키는 것이 대형 유출 사고의 단골 경로다.**
설치 직후 기본 설정이 외부 접속을 허용하는 제품도 있고,
"접속이 안 된다"는 이유로 직접 열어버리는 경우가 더 많다.

스캔 봇은 열린 DB 포트를 **몇 시간 안에** 찾아내고, 흔한 비밀번호부터 대입한다.

---

## 점검 1 — 어느 주소에서 듣고 있나

> 📁 리눅스 프롬프트

```bash
ss -tln
```

`ss` = 열려 있는 포트 조회. `-t` TCP, `-l` 대기 중(listen), `-n` 이름 대신 번호로.

| 출력 | 판정 |
|---|---|
| `127.0.0.1:5432` | ✅ **안전** — 자기 자신만 |
| `0.0.0.0:5432` | 🚨 **위험** — 모든 주소에서 받는 중 |

웹서버(nginx)는 `0.0.0.0`이 정상이다. **DB가 `0.0.0.0`이면 문제.**

---

## 점검 2 — 설정 파일 두 개

> 📁 리눅스 프롬프트

```bash
sudo grep -n "listen_addresses" /etc/postgresql/16/main/postgresql.conf
```

| 값 | 판정 |
|---|---|
| `#listen_addresses = 'localhost'` (주석) | ✅ 기본값 `localhost` 적용 — 안전 |
| `listen_addresses = 'localhost'` | ✅ 안전 |
| **`listen_addresses = '*'`** | 🚨 **모든 주소에서 듣는 중** |

> **주석(`#`)으로 적힌 값은 "이게 기본값"이라는 안내다.** 설정을 안 하면 그 값이 적용된다.

> ⚠️ 인터넷 검색에서 "접속이 안 되면 `'*'`로 바꾸라"는 안내를 자주 보게 된다.
> **그게 노출 사고의 시작이다.** 외부 접속이 정말 필요하면 주소를 특정하고 방화벽을 함께 건다.

```bash
sudo grep -v "^#" /etc/postgresql/16/main/pg_hba.conf | grep -v "^$"
```

**HBA** = Host-Based Authentication = 접속 지점 기반 인증.

칸 구성: `TYPE  DATABASE  USER  ADDRESS  METHOD`

| 칸 | 값 | 뜻 |
|---|---|---|
| TYPE | `local` | 소켓 — 같은 서버 안. 네트워크 안 거침 |
| TYPE | `host` | 네트워크(TCP/IP) |
| ADDRESS | `127.0.0.1/32` | 자기 자신만 (IPv4) |
| ADDRESS | `::1/128` | 자기 자신만 (IPv6) |
| ADDRESS | **`0.0.0.0/0`** | 🚨 **어디서든** |
| METHOD | `peer` | 리눅스 계정 = DB 계정이면 통과 |
| METHOD | `scram-sha-256` | 비밀번호 확인 (암호화) |
| METHOD | **`trust`** | 🚨 **비밀번호 없이 통과** |

**확인할 것:** `host` 줄의 ADDRESS가 `127.0.0.1/32`, `::1/128` 외의 값이 있는가.
그리고 METHOD에 `trust`가 있는가.

## 점검 3 — 실제로 뚫어본다

> 📁 리눅스 프롬프트

```bash
hostname -I          # 이 서버의 IP 확인
psql -h <그 IP> -U app_user -d mysite
```

`127.0.0.1`이 아닌 **자기 IP로** 접속을 시도한다. 거부돼야 정상.

| 결과 | 뜻 |
|---|---|
| **`Connection refused`** | ✅ **아무도 안 듣고 있음** — 원하는 결과 |
| `password authentication failed` | ⚠️ **서버에 닿았다.** 듣고 있다는 뜻 — 설정 재확인 |
| `timeout` | 방화벽이 조용히 막는 중 |

> 오류 종류를 구분하는 게 핵심이다.
> `Connection refused`는 **닿지도 못한 것**, `password ... failed`는 **닿았는데 인증만 실패**한 것.

## 다층 방어 (defense in depth)

```
① listen_addresses   →  외부 주소에서 아예 안 듣는다
② pg_hba.conf        →  들었더라도 외부 주소는 거부한다
③ 방화벽(ufw)        →  포트 자체를 막는다
```

한 겹이 뚫려도 다음 겹이 막는다. **실수로 ①을 열어도 ②가 남아 있으면 여전히 안전하다.**
VPS에서는 ③까지 반드시 건다.

## 배운 것

**1. DB는 앱만 부를 수 있으면 된다**

```
인터넷 → 방화벽 → nginx(0.0.0.0) → 앱 → DB(127.0.0.1)
                    ↑ 열려야 함        ↑ 닫혀 있어야 함
```

바깥에서 DB에 직접 닿을 이유가 없다. 관리가 필요하면 SSH로 서버에 들어간 뒤 접속한다.

**2. 기본값이 안전한 제품인지 확인한다**

Ubuntu의 PostgreSQL 패키지는 기본값이 `localhost`라 안전하게 설치된다.
**모든 DB가 그런 것은 아니다.** 설치 직후 반드시 점검 1을 실행한다.

**3. 앱은 전용 계정으로 연결한다**

관리자 계정(`postgres`)은 `Bypass RLS` 권한이 있어 행 단위 보안을 무시한다.
Supabase의 Secret key와 같은 성격. 앱에는 필요한 권한만 준 전용 계정을 준다.
